# Перенос агентного режима в новый проект

Пошаговая инструкция: как развернуть этот комплект в другом репозитории (Python/FastAPI,
Node.js/React, или любом другом стеке).

## Шаг 1. Скопировать файлы агентов

```bash
cp -r agents_template_improved/.qwen <new-project-root>/.qwen
```

Это даёт: `.qwen/agents/{spec-writer,backend-dev,frontend-dev,qa,adversary}.md` и
`.qwen/skills/task-spec/{SKILL.md,TEMPLATE.md}`. Эти файлы универсальны — их обычно
не нужно править. Правка нужна только если:
- в проекте другой набор ролей (например, нет frontend-dev — API-only проект);
- модели по умолчанию нужно сменить (правка `model:` во frontmatter).

## Шаг 2. Создать QWEN.md и AGENTS.md

Скопируй `QWEN_TEMPLATE.md` → `QWEN.md` и `AGENTS_TEMPLATE.md` → `AGENTS.md` в корень
нового проекта. Заполни блоки `{{...}}`:

- **Обзор проекта:** 2–5 предложений о назначении.
- **Стек:** таблица язык/фреймворк/ORM/линтеры — как в проекте на самом деле.
- **Архитектура:** точка входа, модульная структура, дерево директорий.
- **Сборка и запуск:** реальные команды (`npm install`, `uv sync`, `poetry install`...).
- **Соглашения разработки** (в AGENTS.md): стиль кода, паттерн модуля, конфигурация.
- **Грабли:** известные ловушки — cwd-зависимости, побочные эффекты импорта, etc.

Держи проектные части QWEN.md и AGENTS.md синхронными (это уже заложено в шаблоне).

## Шаг 3. Заполнить таблицу «Зоны и проверки»

Ключевая точка адаптации — таблица в AGENTS.md, раздел «Агентный режим»:

```markdown
| Агент | Зона (можно редактировать) | Чем проверяет изменения | Особые запреты |
|---|---|---|---|
| frontend-dev | src/components/, src/pages/ | npm run build, npm run typecheck | src/api/ (зона backend) |
| backend-dev  | src/api/, src/db/, migrations/ | ruff check, alembic upgrade, curl | src/components/ |
| qa | tasks/current/e2e/, DEFECTS.md | curl-сценарии, npm test | код продукта |
| adversary | tasks/current/ADVERSARIAL_REVIEW.md | curl, логи | всё кроме своих файлов |
| spec-writer | tasks/current/REQUIREMENTS.md (фаза создания) | чек-лист task-spec | код продукта |
```

Агенты читают эту таблицу как единственный источник истины о том, что можно
редактировать и чем проверять. Сам текст ролей (`.qwen/agents/*.md`) не меняется.

## Шаг 4. Создать структуру tasks/

```bash
mkdir -p <new-project-root>/tasks/current
```

Заполни `tasks/current/REQUIREMENTS.md` заглушкой:

```markdown
# Задания нет

Текущего задания нет. Положите сюда сырую идею задания (2–10 строк) — оркестратор
запустит скилл `task-spec` для создания полной спеки.
```

## Шаг 5. Настроить модели (опционально)

Если у тебя другой набор доступных моделей — правь `model:` в frontmatter каждого
`.qwen/agents/*.md`. Модели должны быть объявлены в `~/.qwen/settings.json`. По
умолчанию в этом шаблоне:

| Роль | Модель | Почему |
|---|---|---|
| spec-writer | сильная reasoning-модель | архитектурные решения, оценка объёма |
| backend-dev / frontend-dev | средняя модель баланса скорость/качество | много кода, экономия важна |
| qa / adversary | быстрая модель | curl-сценарии не требуют сильного reasoning |

## Шаг 6. Адаптировать под стек (если не Python/FastAPI)

Файлы `backend-dev.md` и `frontend-dev.md` уже содержат секции best-practices для:
- Python/FastAPI/SQLAlchemy
- Node.js/Express/Fastify
- React/TypeScript

Если стек другой (Go, Rust, Vue, Django) — добавь свою секцию best-practices по
аналогии с существующими (типовые ловушки + примеры кода "плохо/хорошо") прямо в
`.qwen/agents/backend-dev.md` или `frontend-dev.md` своего проекта. Не переусложняй —
только то, что реально пригодится этому стеку.

## Шаг 7. Первый запуск

1. Пользователь пишет сырую идею в `tasks/current/REQUIREMENTS.md` или в чат.
2. Оркестратор (главная сессия) запускает скилл `task-spec`.
3. spec-writer исследует зону, пишет полную спеку с планом фаз и архитектурными
   решениями.
4. Оркестратор ревьюит по чек-листу, закрывает открытые вопросы с пользователем.
5. После подтверждения плана — исполнение по фазам.

## Частые ошибки при переносе

- **Забыли адаптировать таблицу «Зоны и проверки».** Без неё агенты не знают,
  что можно редактировать в конкретном проекте — это единственная привязка
  универсальных `.qwen/agents/*.md` к твоему стеку.
- **Оставили примеры из донора-проекта** в AGENTS.md/QWEN.md (пути, названия модулей).
  Замени все `{{...}}` — незаполненные плейсхолдеры сразу видно.
- **Слишком широкие фазы для backend-dev/frontend-dev.** Даже с этим улучшенным
  шаблоном превышение бюджета в 1–3 файла на фазу — главный источник перерасхода
  токенов. Спека должна резать заранее.
- **adversary включён по умолчанию.** Он должен появляться в плане только по явному
  запросу пользователя — иначе тратится на задания, где не нужен.
